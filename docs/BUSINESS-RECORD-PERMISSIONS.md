# Business record permissions

In Settings → Roles & Permissions, select a custom internal role and save separate rules for **View list**, **View details**, **Create**, **Edit**, and **Delete**. Every user assigned to that role receives its rules on their next API request. Create is an on/off permission. The other actions support No access, Created by me, Assigned to me, Created or assigned to me, and All records.

This applies to customers, leads, purchases/suppliers, documents, sales orders, services, invoices, expenses, wallets, management records, staff/payroll/documents, and saved CVs. Settings, catalogs, financial administration, dashboard and report entry points keep their existing module switches. Admin and Developer retain full access. Customer Portal roles keep their existing linked-customer restrictions and document-only role editor.

## Ownership

Business roots carry nullable `created_by` and `assigned_user_id` columns. The server stamps the creator at creation, including bulk imports and records generated by another workflow. Clients cannot change the creator. Assignment requires an active internal staff member from the same tenant. Existing records with unknown ownership remain visible through All records; no historical creators or assignees are guessed.

Use **Record assignments**, linked from the role editor, to assign business records. The page only lists records visible to the current role and only saves assignments permitted by its edit scope. Service reassignment uses its existing history and remains limited to open services. The existing service creation, edit, start and sales-order push assignment behavior remains available.

Bill/payment rows, invoice/order lines, lead histories, service assignment histories and dividend distributions/payments inherit their parent's record scope. Replacing child lines is an edit of the parent; it does not require permission to delete the entire parent document. Payroll items and staff documents have their own ownership fields. A staff document's subject (`user_id`) is distinct from the staff member assigned to manage it.

## Enforcement

`recordAccessContext` carries the authenticated user and the route action independently of the existing tenant context. Sequelize query hooks add ownership predicates with AND, including eager associations, separate queries, count and aggregate queries. This covers searches, employee tracking, dashboard totals, reports and exports. Private file routes and PDF routes use detail access. List-only responses contain summary fields and omit notes, file paths and child detail collections when the user lacks detail access to that record.

Both instance and bulk writes enforce ownership. A workflow that creates another business root also needs that module's create permission. Editing related business roots or creating entries under an existing parent needs the parent's edit scope. For example, a payment needs access to edit the selected wallet, and posting a supplier bill needs access to edit that supplier. Newly created records can receive their initial child lines within the same request. Staff directories expose only fixed identity fields; numbering and subscription-limit checks deliberately count the whole tenant without exposing records.

Role JSON uses `{ rules: { list, detail, create, edit, delete } }` per business module. Server normalization validates scope names and derives compatibility booleans for older UI consumers. Legacy roles without `rules` retain their existing read/write/delete behavior until explicitly saved through the new editor. Leads fall back to the legacy customers permission only when no leads permission exists. Fixed administrator roles cannot be renamed into or modified through the role API.

## Schema and checks

The additive startup schema utility and migration `20261018000000-business-record-ownership.js` add missing ownership columns without changing old rows. Rollback preserves recorded ownership. Run regression tests only in the disposable local `docclear_regression_test` database with `TEST_DATABASE_RESET=yes`; the suite guards against running destructive resets on any other database.

Coverage includes all business roots across all five scopes, inherited child scopes, direct detail/PDF/statement access, invoice totals, dashboard/report aggregation, creator stamping and immutability, create-only roles, assignment validation, instance and bulk writes, independent list/detail/edit/delete rules, role saves and tenant boundaries, and repeated additive schema upgrades.
